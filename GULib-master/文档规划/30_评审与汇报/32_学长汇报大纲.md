## 2. 建议讲述顺序

### A. 为什么做

- Graph unlearning 通常把 deletion request 当作普通输入。
- 本项目问：如果攻击者可以策略性选择 deletion set，近似遗忘是否会产生超出 exact retrain 的额外损失？
- 重点不是发明一个永远最强的 selector，而是希望通过系统审计寻找不同 selector 与 GU family 响应背后的可解释性。

### B. Experiment setup（重点）

1. 区分两类对象：GU method 与 deletion selector。
2. 展开四条矩阵轴：method、selector、dataset/backbone/ratio、metric。
3. 讲清完整流程：训练 → 选点 → unlearn → exact retrain → evaluation → evidence。
4. 用 `Total = Drop_retrain + Gap` 区分删除集应有损失与近似算法额外损失。
5. 说明结果为什么需要 artifact、recipe、版本和验收边界。

### C. Threat model：三层 selector 权限

| 层级 | 代表 | 需要的信息 |
|---|---|---|
| L0 · Structural / model-free | degree / PageRank / IM | 图结构，不需要 target 模型 |
| L1 · Target-model black-box transfer | surrogate proper-TracIn | 独立 surrogate，不访问或查询 target 模型 |
| L2 · Direct white-box reference | direct TracIn / GIF | target 梯度、checkpoint 或 Hessian 近似 |

共同前提：攻击者控制 eligible deletion candidates，并能提交删除请求。output-query 作为反馈维度另记，不单独占一层。

### D. Setup readout：一个 cell 如何成为证据

这一段和 [Experiment Config Inventory](../../self/dashboard/config_inventory.html) 配合着看：大纲 / 报告解释阅读方法，实验前端展开全部 config blocks 与实时 produced / usable / rerun；不要把前端数字抄回汇报。

1. 定义 cell：`(dataset, backbone, ratio) × GU method × selector × seed`。
2. 绑定对照：budget-matched random、exact retrain、multi-seed、可选 noise anchor。
3. 分层证据：selection → prediction → evaluation → audit metadata。
4. 从矩阵读出 family heterogeneity、selector sensitivity、scope 与 failure source。
